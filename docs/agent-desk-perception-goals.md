# Agent 桌面感知：目标态

**状态：** 目标定义（非实现规格、非 ADR）  
**实现进度（2026-08-10）：** L0 Survey / Focus+caption / 选中 Inspect / 基础指代已落地；视觉总览落地为按需工具 `look_at_desk`（非每轮强制塞图）。**产品决定不做：** 几何「左边」类相对选中消解、`relative_hints` 文本、**Compare 对照块**。详见 [装配规则](agent-desk-context-assembly.md)、[黄金任务](agent-desk-golden-tasks.md)。

**范围：** 助手如何「描述桌上物件」以及如何「组织上下文看见桌面」

## 1. 问题陈述

当前助手对桌面的感知偏弱：状态栏以类型 + id + 粗糙短标签为主，像素几乎只在「本轮选中」时进入多模态输入。未选中时，助手难以全局理解桌上局面。

设计讨论中容易滑向「眼前第一刀怎么改代码」，而真正需要先钉死的是：

- **物件应该如何被描述**（世界模型字段）
- **上下文应该如何组织**（按任务装配，而不是每轮无脑塞满）

本文只记录**目标态**。分阶段落地应对齐本文分层，但**阶段不定义目标**。

---

## 2. 目标（要什么）

不是「状态栏多写几行」，而是：

**助手对桌面形成一份稳定、可指认、可调度的结构化局面感；在需要时能把细节拉到足够做设计判断的精度；上下文按任务装配，而不是每轮无脑塞满。**

成功时助手应能：

1. **说清桌上有什么**（不依赖用户点选）
2. **指认不歧义**（「那张客厅 / 材质 / 上一版效果」对到稳定 id）
3. **理解关系**（谁从谁来、谁当参考、空间上谁近）
4. **在合适粒度看内容**（目录级 / 关系级 / 画面级 / 像素级）
5. **据此决策**（改哪张、看哪张、以后动手改桌）

「尽可能详细」与「尽可能好组织」是一对张力。目标不是二选一，而是：

**分层真相 + 按需装配。**

## 3. 物件「是什么」：四类描述（缺一类就瘸）

把「物件描述」当成**稳定的世界模型字段**，不是 prompt 里临时拼的散文。

每件物件在目标态应具备四类信息：

| 类 | 问题 | 目标内容 | 不是什么 |
|----|------|----------|----------|
| **身份 Identity** | 这是哪一件？ | 稳定 `id` + 类型 + **可区分名称**（用户命名 / 文件名 / 系统 fallback）+ 生命周期状态 | 不能多件同叫「画布图」 |
| **角色 Role** | 在设计里干什么？ | 源场景 / 参考材质 / 风格参考 / 效果变体等设计与任务用途 | 不只是 `canvas_image` 字符串，也不混入生成中/失败等状态 |
| **结构 Structure** | 在桌面拓扑里在哪？ | 位置（可粗）、显式关系、几何关系、版本血缘 | 不能只有 id 列表 |
| **内容 Content** | 意图和画面分别是什么？ | 意图、短摘要、视觉观察、像素 | 摘要或 prompt 不能冒充像素真相 |

### 3.1 画面描述要不要？

**要，但是第 3 层内容，不是第 1 层身份。**

- 身份解决「哪一张」
- 画面描述解决「画面里大概是什么」
- 像素解决「能否做设计判断与改图验收」

画面描述（caption）是**缓存/提示层**：可错、可过期，绑定文件或版本失效；**不能替代像素**作为最终真相。

### 3.2 派生信息必须带来源

身份与布局主要来自系统，画面描述与角色判断可能来自视觉模型或用户。目标态不能把这些信息都当成同一种事实；每个非原生字段都应能回答「谁提供的、基于哪一版、是否仍然有效」。

建议把派生信息统一理解为带元数据的值：

```text
value              值本身
source             system / user / vision / geometry / generation
derived_from       依赖的 artifact version / file content hash
observed_at        产生或确认时间
stale              是否因源版本变化而过期
confidence         可选诊断字段（见下）；不得单独决定是否采信
```

这不是要求每个字段都向用户展示，而是要求上下文装配器能区分：

- **系统事实**：artifact id、版本、布局、创建者、文件引用。
- **用户事实**：用户命名、用户确认的空间/角色、明确的设计决策。
- **派生观察**：caption、OCR、颜色/材质属性、视觉角色推断。
- **几何推导**：左/右、相邻、重叠、同簇等布局关系。

**是否采信**主要看权威与可核对性，而不是看置信度数字：

1. 系统事实 — 无条件信  
2. 用户事实 — 高权威  
3. 可重算几何 / 显式连线 — 可核对，可信  
4. 视觉/模型观察 — 默认可错；`stale` 与 `derived_from` 优先于分数  
5. 未 Inspect / 指代不唯一 — 不静默选定，列候选或请求确认  

`confidence` 仅作可选诊断（`low | medium | high` 即可，不必连续分数），用于候选排序、日志与调试。**禁止**用「置信度高低」单独决定是否写入决策、是否覆盖用户命名/当前 desk revision、或是否静默完成指代消解。LLM 自报高分校准差，不能当作真值门闸。

派生信息可以帮助助手调度，但不能覆盖更高权威级别的事实；没有 Inspect 或明确来源时，也不能把推断说成像素事实。

### 3.3 角色是上下文角色集合，不是单一类型

`artifactType` 只说明记录形态，不足以说明它在当前设计中的用途。同一物件可能同时是候选变体、某次生成的结果，也可能被另一张图当作参考。因此目标态的 `role` 应允许多个值，并记录来源与适用范围，例如：

```text
source_scene          主场景源图
reference_material    材质或家具参考
reference_style       风格参考
generated_variant     生成出的候选变体
```

角色最好区分「物件的长期语义」与「本轮任务中的临时角色」。例如一张效果图可以在本轮作为 `source_scene`，在另一轮作为 `reference_style`；这不应改写它的身份。

空占位、生成中、生成失败等属于生命周期状态，不属于角色；它们可以影响上下文调度，但不能回答物件在设计中「用来做什么」。

### 3.4 名称采用三层策略

目标态同时保留：

1. 稳定的内部 `artifactId`，用于工具和审计；
2. 用户可修改的 `displayName`，表达设计师自己的称呼；
3. 系统生成的 fallback name，在没有用户命名时帮助区分物件，例如「客厅户型图」「浅橡木材质参考 1」。

生成意图或 prompt 摘要属于内容/意图字段，不直接充当身份名称。这样 prompt 改变、版本增加或视觉描述更新时，物件仍然是同一件可指认的东西。

## 4. 内容分层（由粗到细）

```
L0 目录：id, type, name, status, pose, links
L1 语义：role 推断, cluster, 血缘摘要
L2 内容摘要：caption / prompt 全文 / 关键属性
L3 感知：像素（或局部 crop）
```

| 层级 | 用途 | 成本 | 默认是否进入每轮上下文 |
|------|------|------|------------------------|
| **L0** | 全局不盲、可指代 | 低 | **是**（全桌目录，可截断摘要） |
| **L1** | 调度与关系推理 | 低–中 | **宜默认或近默认**（至少连线/血缘） |
| **L2** | 无像素时的粗理解 | 中（生成/缓存） | **焦点相关**，非全桌默认 |
| **L3** | 改图、对比、验收 | 高 | **按需 Inspect**，非全桌默认 |

能力映射：

- **全局调度** → L0 + L1  
- **指代与粗理解** → L0–L2  
- **改图与验收** → 必须 L3
- L2 永远是辅助；L3 是最终依据

### 4.1 L2 进一步拆分意图与观察

`prompt` 和图片内容不是同一类信息。目标态至少区分：

- **Intent**：用户或 Agent 想生成/修改什么；来源通常是用户或生成记录。
- **Visual observation**：图片实际呈现了什么；来源是视觉 Inspect，默认可错，须带来源与失效信息。
- **OCR / attributes**：图中文字、颜色、材质、家具、灯光等可检索属性。

例如「生成原木风客厅」是意图，不等于最终图片一定呈现了原木风。助手可以引用意图来理解设计过程，但在判断画面是否真的达到目标时必须依赖 L3 像素，或明确标注为视觉观察。

「尽可能详细」的正确含义：

- 系统**能到达 L3**
- L0–L2 在目标态**默认足够完整**
- **不是**每轮把全桌 L3 塞进上下文

## 5. 上下文如何组织（目标原则）

### 5.1 桌面是世界模型，对话是任务

| 概念 | 含义 |
|------|------|
| **World state** | 当前桌面的结构化快照（权威局面） |
| **Task context** | 本轮用户意图 + 选中 + 相关子图 |
| **Episode memory** | 本 thread 已发生的工具轨迹（模型侧会话历史） |

助手「看见桌面」= **读 world state 的投影**，不是「聊天记录里碰巧提到过」。

World state 是从 Artifact、桌面布局、显式关系和可重算派生信息编译出的**权威读模型**，不是与这些事实源并行维护的第二份业务数据；写桌工具仍修改原始事实源，再由感知模块重新投影。

### 5.2 每轮上下文 = 固定骨架 + 任务相关展开

目标装配顺序（同时服务于注意力与 KV 友好）：

```
[稳定 system：身份与工具纪律]
[本轮用户话 + 附件]
[桌面局面：L0 全量目录 + 关系图]
[焦点：选中 / 用户点名 / 任务相关子图 → 升到 L2/L3]
[进行中任务 / 最近变更]
```

规则：

- **全量**只保证「不盲」：L0（+ 必要 L1）
- **详细**只保证「不瞎做」：对焦点升采样到 L2/L3
- **选中 = 强焦点，但不是唯一眼睛**；无选中也能从目录导航再升采样

### 5.3 「尽可能详细」是策略，不是一次塞满

| 模式 | 何时 | 看到什么 |
|------|------|----------|
| **Survey 扫视** | 默认每轮 | 全桌 L0 + 连线 + 状态 |
| **Focus 聚焦** | 有选中 / 指代消解后 | 焦点物件 L2 + 邻接/血缘一跳 |
| **Inspect 细看** | 要判断画面或准备改图 | 该物件 L3 像素 |

**不做 Compare：** 多版对比不单独开模式；多选 → Focus（多 core）+ Inspect。  
「好组织」= 在 Survey / Focus / Inspect 间升采样，而不是永远 Survey 或永远 Inspect。

### 5.4 Survey 需要视觉总览投影

L0/L1 能让助手不盲，但文本目录仍然缺少整体视觉构图。目标态应具备**带短编号的桌面总览图**能力：按桌面布局放置缩略图，标出 `A01/A02` 等 alias，选中物件高亮，显式连线可见。

**落地选择（已定）：** 总览为助手**按需工具** `look_at_desk`（toolResult 附图 `role=desk_overview`），**不是**每轮 Survey 默认多模态注入。文本 Survey 仍每轮必有；需要局面感时再调工具。人用画布 minimap 与 agent 总览解耦。

总览只建立整体局面感和编号对应，不承担精细设计判断；材质、比例、细节或验收仍升到对应物件的 L3 Inspect。视觉输入须有明确角色（overview vs inspect），不能只把无标签的图片数组交给模型。

### 5.5 指代消解是一等能力

目标：用户说「材质那张」「A03」「上一版 / 源图」时，系统应产出 **resolved ids**，再进入 Focus / Inspect。  
**不做：** 「左边 / 右边那张」等纯几何相对选中消解（靠点选、alias 或可区分名称）。

描述模块不只是「打印桌面」，还要支持：

```
name / role / spatial / link → artifact id
```

指代消解的结果应显式产出 `resolved ids` 及其依据，而不是只在自然语言中猜测：

```text
「材质那张」→ A02
依据：role=reference_material，displayName/fallbackName 命中（唯一）
权威：user/system 字段优先于 vision caption
```

无法唯一消解时，助手应列出候选并请求确认；不得因为视觉 caption 相似或模型自报高置信就静默选择另一件物件。

### 5.6 当前桌面必须压过历史桌面

桌面状态是 world state，不是聊天历史的附属摘要。每次注入的桌面投影都应带有可比较的 `revision` 或等价版本标识，并明确当前性：

```text
[DESK_CONTEXT current=true revision=...]
```

目标规则：

- 只有最新的 `current=true` 桌面投影是当前局面的权威依据；
- 历史投影可以解释过去发生过什么，但不能覆盖当前物件、位置、版本或存在性；
- 物件删除、版本替换、文件变化后，依赖旧版本的 L1/L2 派生信息标为 `stale`；
- 助手不能把历史中曾经存在的物件当成当前仍在桌上的物件。

## 6. 目标能力边界（眼睛侧）

在写桌「手」尚未齐全之前，感知模块目标应能支撑：

1. **局面报告**：桌上 N 件、几条链、哪些 pending  
2. **无歧义指认**：自然语言 → artifact id  
3. **关系推理**：主源 / 参考 / 后代效果图  
4. **按需升采样**：决定何时用 caption、何时拉像素  
5. **诚实**：未 Inspect 过就不能假装看过像素细节  

以后的「手」（移动、连线、生图等）应对**同一 world model** 做写操作；眼睛先定义**读模型**。

## 7. 与「眼前实现」的区别

| 眼前实现思维 | 目标思维 |
|--------------|----------|
| 先改 `desk-status` 多拼几行 | 先定义 world model 字段与投影规则 |
| 第一刀不做 caption | caption 是内容层目标，排期可后，**语义位置要先定** |
| 选中才有图就够用一阵 | 选中只是焦点，不是视觉能力上限 |
| 能评测再谈结构 | 结构是目标本体；评测是验收手段 |

可以分阶段落地，但阶段应对齐 **L0→L1→L2→L3** 与 **Survey→Focus→Inspect**，而不是用阶段重新定义目标。

| 目标 | 现状 |

## 9. 尚未拍板的目标决策（附建议）

这些是**目标形态**选择，不是实现细节：

1. **名称权威**：建议系统 fallback + 用户可改显示名，两者并存；artifact id 永远是机器权威。
2. **位置语义**：机器保留绝对布局；Survey 可投影粗 grid。**不做**相对方位 harness 指代（「左边那张」）；指认靠点选 / alias / 名称。
3. **关系语义**：显式关系（连线/血缘/参考）进上下文并可持久化。左/右/相邻等几何关系**不**做 harness 指代消解，也**不**注入 `relative_hints`；Survey 可保留粗 grid 供人读，不承诺模型侧方位消解。
4. **Caption**：建议持久化为独立的可重算缓存，不写入 Artifact payload；按文件内容 hash、artifact version 和 analyzer version 失效。
5. **详细度上限**：建议以 token、图片张数和总字节预算共同约束，而不是只规定物件数量；超过预算时优先保留当前焦点、其关系一跳和 L0 目录，其余降级为索引。
6. **视觉总览**：能力必备；**触发已定为按需工具**（非每轮 Survey 默认塞图）；总览只建立布局和编号对应，不替代单物件 Inspect。

## 11. 一句话

**桌面感知的目标 = 结构化世界模型（身份/角色/结构/内容）+ 分层内容（L0–L3）+ 按任务的看见模式（Survey/Focus/Inspect；无独立 Compare）；详细是能力可达，组织是默认投影与升采样纪律。**
