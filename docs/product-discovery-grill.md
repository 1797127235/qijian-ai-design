## 1. 产品方向

目标是打造一个面向建筑、室内设计师的 AI 设计平台，初步应用场景包含：

- 家装
- 工装
- 景观

产品不定位为单纯的文生图工具，而是面向专业设计流程的 AI 工作台。核心价值是让 AI 参与前期设计提案，同时保留设计师的判断、修改和最终控制权。

## 2. 第一阶段用户与切入点

### 核心用户

第一批用户确定为：

> 中小型室内设计工作室的一线设计师。

### 首个业务切口

第一阶段聚焦：

> 中高端家装项目的前期方案提案。

具体项目范围收窄为：

- 90～150㎡城市住宅
- 两到三居室
- 普通改造项目

暂不优先覆盖：

- 别墅和超大平层
- 老旧房结构改造
- 极端异形户型
- 复杂机电和全屋智能
- 大量定制结构的项目

### 核心价值假设

将设计师从 Brief 到第一版客户提案的时间，从约 3～7 天压缩到半天，同时让设计师保留最终控制权。

第一版产品的目标不是自动完成全部设计，而是加速：

- 需求整理
- 设计方向探索
- 概念效果图生成
- 材质与家具组合
- 客户提案组织

## 3. MVP 输入与输出

### 输入边界

第一版接受：

- 户型图图片或 PDF
- 面积、家庭成员、预算、功能需求等文字信息
- 业主或设计师提供的参考图片

第一版不承诺 DWG 的精确解析和施工级几何闭环。

### 几何精度承诺

默认几何精度为 `conceptual`：

> 保持主要空间关系、开口、动线和家具关系，但不承诺施工级尺寸。

现阶段几何可信度分为：

- `style_only`：只参考风格和氛围，不保证户型关系；
- `conceptual`：保持主要空间关系和设计意图，尺寸允许近似；
- `measured`：仅在资料带有清晰标注尺寸时使用，仍需人工复核。

所有提案应明确：

> 本方案用于前期概念沟通，尺寸、结构、机电及施工条件需由专业人员复核。

### 首个 AI 输出：项目理解卡

上传资料后，AI 不直接生成效果图，而是先生成“项目理解卡”，由设计师确认。

项目理解卡包含：

- 项目类型和面积
- 房间/空间识别结果
- 主要门窗和开口
- 可能的动线关系
- 业主需求摘要
- 风格与材质偏好
- 已识别的硬约束
- AI 不确定或需要人工确认的内容

设计师可以修正房间用途、不可拆墙体、厨房功能、预算限制等信息。

### 设计方向卡

Brief 确认后，AI 先生成 2～3 张低成本设计方向卡，不立即生成完整效果图。

每张方向卡包含：

- 方向名称和一句话概念
- 空间策略
- 色彩和材质组合
- 代表性家具、灯具和软装
- 适合的生活方式
- 参考图或情绪板
- 可能的设计风险
- 与其他方向的明确差异

设计师可以选择一个方向、退回并说明不满意的地方，或修改局部属性后重新生成。第一版不支持组合多个方向。

### 核心提案包

设计师确认方向后，系统生成一套可用于第一次客户沟通的提案包：

- 2～3 个方向（或最终选定方向的完整说明）
- 每个方向 3～4 张关键空间效果图
- 材质/家具情绪板
- 设计说明
- 空间策略
- 资产来源和引用关系

第一版不输出：

- 施工图
- DWG
- BIM
- 精确预算
- 可直接采购的工程清单

### 第一版交付格式

- 可分享网页
- PDF 提案包
- 单张高清图片
- 内部保留结构化 Artifact、资产引用和版本记录

## 4. 产品工作流

```text
上传户型图/PDF + 需求 + 参考图
        ↓
项目理解卡
        ↓ 设计师确认
2～3 张设计方向卡
        ↓ 设计师选择/组合
方案约束包
        ↓
多空间效果图与提案包
        ↓ 设计师确认
网页 + PDF + 高清图片
```

### 四个人类确认门

1. **Brief 确认**：面积、家庭成员、预算、功能需求和硬约束；
2. **设计方向确认**：从 2～3 个方向中选择一个；第一版不支持组合多个方向；
3. **方案约束确认**：确认八个家装约束模块、禁止项、来源和冲突处理后，才允许进入后续设计；
4. **提案包确认**：确认效果图、材质、家具和文案后才标记为可交付。

确认门之间，skill 可以自动生成变体、做局部修改、补充说明、组织资产和检查一致性，但不能静默修改已经确认的户型关系、预算、核心风格或明确排除的内容。

## 5. 平台、Artifact 与 skill 的关系

```text
平台界面 / API
        ↓
空间设计领域 Artifact 层
        ↓
design-proposal skill
        ↓
图像、文案、页面等生成工具
```

### 平台层负责

- 项目、用户和权限
- 文件上传
- 设计画布
- 版本浏览和回退
- 协作、评论和审批
- 网页、PDF 和图片交付

### Artifact 层负责

作为平台与 skill 之间的正式领域数据契约，保存结构化项目事实。它不是传统消息队列，而是空间设计领域状态层和 Agent 工具调用契约。

第一批 Artifact 类型：

1. `project_brief`：项目类型、面积、用户、预算、目标和约束；
2. `site_or_floorplan`：户型图/场地资料、尺寸可信度和解析结果；
3. `design_directions`：2～3 个设计方向及差异；
4. `asset_manifest`：图像、材质、家具、植物和文字的来源与角色；
5. `proposal_packet`：当前可交付提案包；
6. `decision_log`：用户确认过的选择、修改和版本关系；
7. `design_system`：已确认的空间约束、风格、材料、家具和禁止元素。

### Artifact 版本机制

Artifact 采用不可变版本和 `current` 指针：

```text
project_brief.v1.json       confirmed
project_brief.v2.json       superseded
project_brief.current.json  -> v2
```

每个版本至少记录：

- `artifact_id`
- `version`
- `status`：`draft` / `confirmed` / `superseded`
- `parent_version`
- `created_by`：`user` / `agent` / `tool`
- `created_at`
- `change_reason`
- `input_refs`
- `content_hash`

### skill 的定位

`design-proposal` 作为平台内部的提案生成编排内核，不直接作为用户界面。

保留它擅长的部分：

- 素材读取
- 设计方向确认
- 资产清单
- 用户确认门
- 失败兜底
- 交付审计

平台自己负责项目、用户、权限、版本和设计画布。

## 6. skill 优化方向

现有 `/home/liu/桌面/design-proposal/` 的优势：

- 五阶段流程清晰；
- F1～F11 失败兜底完整；
- B1～B13 反例黑名单有实际工程价值；
- 有资产来源、路径约束、输出哈希和页面审计；
- 有离线工具、项目目录和可追溯的生产管线。

主要错位：

- 当前更偏素材驱动的作品生产和视频/网页交付；
- `proposal_packet` 仍包含视频时长、目标平台、配音和音乐等字段；
- `design_intake` 缺少户型、面积、家庭成员、预算、房间关系和空间约束；
- 渲染器主要负责 HTML 物化，不等于设计工作台；
- 页面审计不能替代空间动线、几何关系和多视图一致性检查。

优化原则：

> 通用核心 skill + 家装/工装/景观适配器。

通用核心负责理解项目、读取素材、提炼意图、管理资产、生成和审查提案、记录决策、处理失败和版本。场景适配器分别定义家装、工装和景观的领域字段、约束、质量检查和提案模板。

视频、Blender、Web3D 等能力暂时降为后续扩展，不进入家装 MVP 主路径。

## 7. 编辑与一致性

### 首批编辑能力

效果图生成后，提供：

- 自然语言指令；
- 区域选择；
- 元素锁定。

示例：

- 选中沙发区域：“换成低矮的米色模块沙发”；
- 选中墙面：“改成浅灰微水泥，保持灯光不变”；
- 锁定厨房和地板：“只调整餐厅灯具和餐桌”。

每次修改都生成新版本，并记录修改区域、指令、保留元素、替换资产以及新旧图像的关联。

### 方案约束包

每个已确认方向生成一份 `design_system.vN.json`，所有后续图像引用同一份约束包。

约束包至少包含：

- 空间关系和不可变几何
- 设计概念
- 色彩调色板
- 已确认的材料 ID
- 家具和灯具 ID
- 植物/软装 ID
- 光线和时间设定
- 禁止出现的元素
- 每个资产的参考图和来源
- 已确认的设计决策

## 8. 资产、隐私与协作

### 资产来源

采用三层资产来源：

1. **平台精选资产**：有固定 ID、标签、参数、来源和授权信息；
2. **设计师上传资产**：工作室自己的品牌材料、常用家具和案例；
3. **外部参考素材**：只作为 `reference_only`，未确认授权的素材不进入最终交付。

### 隐私原则

- 项目默认私有；
- 素材默认不用于模型训练；
- 设计师明确发布后，素材才进入团队资产库；
- 平台公共资产必须经过授权和脱敏；
- 记录上传者、项目归属、素材来源、授权状态和分享范围。

### 协作范围

第一版不做实时多人共同编辑，采用：

- 项目负责人：上传资料、确认 Brief、选择方向、修改方案；
- 协作者：查看、评论、提供素材；
- 客户/评审者：只读预览和反馈。

### 客户反馈

客户通过提案链接只读浏览，并对页面、空间或资产发表评论。反馈类型包括：

- `comment`
- `request_change`
- `approve`
- `reject`
- `question`

客户不能直接修改核心 Artifact。设计师确认后，才将反馈写入 `decision_log.vN.json`，再由 skill 生成下一版方案。

## 9. 模型与工具架构

平台和 skill 不绑定某一个 AI 模型或供应商，只绑定能力接口：

- `vision_parse`
- `brief_reasoning`
- `direction_generation`
- `image_generation`
- `image_editing`
- `consistency_check`
- `proposal_writing`

每次调用记录 provider、model、prompt 版本、输入 Artifact 版本、输出质量、失败原因、成本和耗时。

## 10. MVP 验收标准

使用真实项目进行验证：

- 3～5 名设计师；
- 至少 10 个真实前期提案项目；
- 与设计师原有流程对比耗时；
- 统计 AI 产出的保留、修改和丢弃比例。

通过标准：

1. 前期提案时间至少减少 50%；
2. 至少 70% 的项目保留 AI 输出中的一部分；
3. 没有严重违反已确认户型关系或硬约束的问题；
4. 设计师愿意在下一个项目继续使用。

## 11. 已明确暂不讨论

- 付费和商业模式；
- 具体模型供应商和成本；
- 原生桌面端或移动端；
- 实时多人共同编辑；
- 施工图、DWG、BIM 和精确预算；
- 景观与工装适配器的详细字段；
- 生产环境部署和多租户基础设施。

## 13. 后端启动决策

### MVP 身份与归属

第一版不实现注册、登录或第三方 OAuth。开发环境使用一个预置的开发设计师身份调用 API；但所有项目和 Artifact 从数据库第一天起都保存 `owner_id`，并在 API 层保留按归属进行授权校验的边界。

这样可以先验证项目与 Artifact 流程，同时避免后续引入真实认证时迁移无归属数据或重写资源权限模型。真实身份认证将在项目流已被验证后接入。

### 首批 API 资源

第一批后端只实现 `projects` 和 `artifacts`：

- 项目保存归属和基本项目信息；
- Artifact 保存设计 Brief、项目理解卡、方向卡等可审阅、可版本化的成果；
- 上传文件先作为 Artifact 的关联输入，不在本切片中单独建设设计资产资源。

这个边界覆盖首个家装工作流，同时让资产库、评论和客户预览可以在验证后独立演进。

### Artifact 存储形态

Artifact 使用通用版本信封加类型化 JSON 内容：

- 信封保存稳定的跨类型字段：`artifact_id`、`project_id`、`artifact_type`、版本、状态、创建者、输入引用与创建时间；
- `payload` 保存各 Artifact 类型的业务字段，并在 API 写入前按对应 Schema 校验；
- Brief、项目理解卡、方向卡共享版本契约，但不被迫共享不相干的领域字段。

### 首批数据库实体

首批数据库包含：

- `designers`：当前预置开发设计师，后续可承接真实认证身份；
- `projects`：设计项目与 `owner_id`；
- `artifacts`：Artifact 稳定身份、项目归属与当前版本指针；
- `artifact_versions`：每次变更产生的一条不可变内容记录。

`artifacts` 与 `artifact_versions` 分表，避免将当前状态和历史审阅记录混在同一行中。

### API 版本与写入语义

首批 API 使用 `/api/v1` 路径。核心写入接口为：

- `POST /api/v1/projects` 创建项目；
- `POST /api/v1/projects/{id}/artifacts` 创建 Artifact；
- `POST /api/v1/artifacts/{id}/versions` 追加不可变版本。

读取当前版本由服务端根据 Artifact 的当前版本指针解析。Artifact 不使用 `PATCH` 覆盖核心内容，以保持审阅与追溯语义一致。

### 文件存储边界

首批实现定义 `Storage` 接口，开发环境使用本地文件系统适配器。数据库仅保存文件元数据、内容哈希和对象键；Artifact 通过输入引用关联文件。

该接口为后续 S3/OSS 等兼容对象存储保留替换空间，不改变项目和 Artifact API。

### 首个后端纵向链路

第一条可交付链路限定为：创建家装项目，保存设计 Brief 的首版，并读取项目、Brief 当前版和历史版本。户型图、参考图或 PDF 可以作为可选上传资料关联到 Brief。

项目理解卡与方向卡将直接复用这套 Artifact API，在后续链路中接入生成逻辑，而非预先建设专用数据接口。

## 14. 方向生成阶段共识

项目理解确认后，下一阶段只开发设计方向卡，不直接生成效果图。设计师点击明确的“生成设计方向”按钮后，系统使用已确认的项目理解版本及其输入引用创建一次方向生成任务。

一次任务生成一个 `design_directions` 方向集，包含三张可比较的方向卡。三张卡必须在空间组织策略和设计取舍上不同；色彩、材料、家具和灯光只作为视觉语言，不得成为方向差异的唯一依据。第一版不生成图片、不虚构品牌或商品信息。

方向卡固定包含：方向名称、一句话概念、空间策略、关键取舍、材料与色彩、家具与灯光语言、适合的生活方式、设计风险与待确认点、与其他方向的区别。字段长度受限，内容可由设计师编辑。

设计师可以编辑方向卡、单卡重新生成，或选择一个方向确认。第一版暂不支持组合多个方向。生成失败保留任务记录并允许重试，不使用静态或模拟结果填充。

## 15. 参考图与方案约束包

方向生成前支持真实参考图上传、预览、删除和与 Brief 关联。参考图只影响视觉语言，不改变 CAD 几何、空间关系和已确认硬约束。

方向确认后，系统自动生成 `design_system` 方案约束草稿。约束包可编辑，但每次编辑都产生新草稿版本，必须再次确认后才能进入后续设计。方向卡阶段不宣称完成几何一致性验证；该检查属于后续效果图阶段。

## 16. 方案约束包 grilling 共识

本节记录 2026-08-03 通过 `grill-with-docs` 形成的产品决策。完整的不可逆契约见 [`docs/adr/0009-design-constraint-package-contract.md`](./adr/0009-design-constraint-package-contract.md)。

### 产品定位

方案约束包的第一消费者是设计师及其设计团队。它是已确认方向的可执行设计依据，不是客户提案、效果图提示词或施工图。确认方向后自动生成草稿，设计师编辑并确认后才生效。

### 范围与模块

第一版只落地家装适配器，保留工装和景观扩展位。家装包固定包含结构与户型边界、空间组织原则、动线与关系、功能与收纳、材料与色彩边界、家具与灯光原则、预算与实施边界、待确认事项八个模块，并单独记录禁止项。

### 信任边界

约束包不修改 CAD 几何。每条约束记录来源类别（来源事实 / 设计决策 / 设计师添加）和约束强度（硬约束 / 软约束 / 待确认），不使用 AI 置信度。方向和项目事实冲突时标记冲突并交给设计师决定。

### 编辑、语言与版本

设计师可以编辑、新增、删除、排序任意约束。单模块重新生成只产生候选草稿，不覆盖现有内容。所有保存先是草稿，确认后追加不可变版本；项目理解或设计方向有新确认版本时，旧包标记为需要复核。方案约束包跟随用户主要工作语言，来源中的 CAD 图层名、品牌名和专业缩写保留原文。

### 界面与验收

方案约束包使用单项目结构化编辑页，提供模块导航、主编辑区、来源回溯和版本确认，不使用三列长卡片。第一版验收必须覆盖自动生成草稿、逐条来源和强度、八个模块、禁止项、单模块重生成、冲突、编辑、版本历史和来源回溯；不生成效果图、施工图或精确工程清单。

## 17. 结构化无限画布 grilling 共识

本节记录 2026-08-03 通过 `grill-with-docs` 形成的提案画布决策。不可逆领域契约见 [`docs/adr/0010-structured-proposal-canvas-contract.md`](./adr/0010-structured-proposal-canvas-contract.md)，实施顺序见 [`docs/implementation/structured-proposal-canvas-mvp.md`](./implementation/structured-proposal-canvas-mvp.md)。

### 画布定位

提案工作台采用结构化无限画布。它是设计师工作面，不是通用节点图、自由白板、CAD 编辑器或客户展示页。正式界面使用左侧项目依据、中间以户型和空间区域为核心的画布、右侧当前节点检查器；桌面端完整编辑，移动端只查看和评论。

### 空间地图与关系

设计方向与方案约束确认后，AI 先提出空间锚点，设计师在来源图纸上校正空间多边形、名称、用途、关键空间和有类型关系。每张图纸页面对应一张空间地图，多楼层项目可以引用多张地图。空间地图整体不可变版本化，不编辑墙体、门窗、楼梯、管线、开口或施工尺寸。

### 提案、资产与版本

每个画布只绑定一个确认方向、一版确认约束包和确认空间地图。画布选择关键空间后创建空间提案卡；效果图作为空间提案下的变体，资产必须记录来源、空间、角色、输入版本和采用状态。画布节点布局独立保存，不表达领域关系。上游确认版本变化后，下游内容标记需要复核，不自动改写或重出图。

### 交付、反馈与分支

客户提案包从画布中明确采用的空间、资产和说明生成，客户不直接进入画布。客户反馈锚定具体提案内容，设计师确认后才成为设计决策。同一方向下的替代探索使用画布分支；第一版只支持对比和选择，不支持自动合并。

### 第一条实现链路

先实现空间地图、提案画布、空间提案卡和人工资产挂载闭环，不急于接入新的效果图生成。真实出图、客户提案导出、实时协作、CAD 编辑、移动端完整编辑和自动分支合并留在后续阶段。
