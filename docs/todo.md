# 产品与架构待办

## 统一项目资料系统（方案 C）

**状态：** 暂缓，先完成“消息附件与持久来源关系”方案 B。

### 目标

把分散在聊天消息、Artifact 来源和生成结果中的文件统一为项目级资料，使用户能够查看、复用、检索、归档和追踪每份资料的处理状态与使用关系。

### 启动条件

满足以下任一条件后再进入产品设计与工程评审：

- 真实用户频繁需要在不同消息或线程中重复使用同一份资料；
- 用户无法仅通过聊天历史找到曾经上传的资料；
- OCR、视觉检索、批量处理或多 Agent 协作需要稳定的项目级 Asset 标识；
- 未关联文件、派生预览和来源文件的存储生命周期已经造成可观测成本；
- Artifact 来源审计需要展示完整的“资料 -> 消息 -> 处理结果 -> Artifact 版本”关系。

### 预期范围

- 引入统一 `project_assets` 领域模型，不直接用 `stored_files` 承担业务语义；
- 支持处理状态、失败重试、缩略图、PDF 派生页和元数据；
- 提供项目资料列表以及从资料库重新附加到消息的入口；
- 支持搜索、筛选、归档、删除保护和引用关系查看；
- 统一用户上传、外部导入、Agent 生成文件和导出文件的来源记录；
- 保持 Artifact `inputRefs` 为产物来源的权威契约。

### 当前不做

- 不在方案 B 中增加资料库页面、标签、文件夹或全文检索；
- 不要求用户上传时选择资料用途；
- 不为了未来资料系统阻塞当前对话附件闭环。

### 前置工作

1. 完成方案 B，并收集附件复用、查找和存储量数据。
2. 观察至少 5 次无引导真实任务，确认资料库解决的是实际行为而非架构偏好。
3. 另行执行产品设计、CEO 评审和工程评审，再决定数据迁移与交互范围。

## 多实例共享文件存储

**状态：** 条件性 P1，启用第二个服务实例前必须完成。

- **What：** 把本地 FileStorage 迁移为 S3/MinIO 等共享对象存储，并保留可替换存储接口。
- **Why：** 数据库可被多个实例共享，但本地上传文件不能；否则 HTTP 上传与 WebSocket Agent 请求落到不同实例时会读取失败。
- **Pros：** 支持水平扩容、统一备份和对象生命周期策略。
- **Cons：** 增加凭证、网络重试、迁移、兼容部署和运维成本。
- **Context：** 当前附件方案明确只支持单实例，禁止用实例粘性路由代替共享存储。
- **Effort：** L（人工）/ M（CC + gstack）。
- **Priority：** P1（仅在多实例部署前生效）。
- **Depends on / blocked by：** 先完成方案 B 的 `AttachmentPipeline` 和 FileStorage 边界。

## 公网认证与项目授权

**状态：** 条件性 P1，任何公网部署前必须完成。

- **What：** 为 REST、WebSocket、文件下载、项目、消息和 Artifact 建立统一身份认证与项目级授权。
- **Why：** 当前 `/api/files/:id` 和其他项目 API 没有账户边界，住宅户型图与设计资料不能安全暴露到公网。
- **Pros：** 建立真实租户隔离、访问撤销和审计基础。
- **Cons：** 涉及账户、会话、权限模型、数据迁移和所有 API，不能用单独签名文件 URL 代替。
- **Context：** 当前版本限定单用户、loopback 或可信内网使用；公网发布必须先完成本项。
- **Effort：** XL（人工）/ L（CC + gstack）。
- **Priority：** P1（仅在公网部署前生效）。
- **Depends on / blocked by：** 需要单独产品设计、威胁模型和工程评审。
