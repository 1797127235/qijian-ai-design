# 结构化提案画布契约

**Status:** accepted  
**Date:** 2026-08-03

## Context

家装前期提案在确认方案约束包后，需要把户型空间、空间提案、效果图变体、材料资产和设计说明组织在同一个设计师工作面中。通用无限白板不能表达空间归属、约束来源、版本影响或客户交付边界；把效果图直接堆在列表中也无法表现空间关系。

第一版必须保持 CAD、户型图与施工级几何的边界。画布服务桌面端设计师工作，不直接面向客户交付。

## Decision

### 画布是结构化工作面

`proposal_canvas` 是绑定一个已确认设计方向、一个已确认方案约束包和一版已确认空间地图的工作面。画布中心以户型图和空间区域为锚点；效果图、材料、家具和批注附着在对应空间附近。连线只可视化已保存的空间关系或引用关系，不是自由装饰线。

画布布局与领域关系分离：节点位置、尺寸、缩放、图层显示和提案叙事顺序属于 `canvas_layout`；它们不改变空间归属、方案约束、资产引用或项目事实。布局可以自动保存草稿和快照，但不能借由拖拽覆盖领域 Artifact。

### 空间地图

`space_map` 是独立 Artifact，记录设计师校正后的空间语义基线。它引用一张来源户型图页面；多楼层或多图纸项目拥有多张空间地图，而不是混用不同坐标系。

空间地图保存归一化坐标的可编辑多边形，每个空间至少包含：

- 稳定 `space_id`；
- 名称、用途和楼层/图纸页面归属；
- 多边形顶点；
- 是否为关键空间；
- 设计师校正状态。

空间关系是有类型的结构化边：`adjacent`、`circulation`、`visual_connection`、`service`、`material_continuity` 和 `separation`。每条关系记录来源事实或设计师说明。

空间地图不编辑、重绘或宣称理解墙体、门窗、楼梯、管线、开口和施工尺寸。AI 可以提出空间锚点，设计师必须校正并确认。修改任一空间区域会产生整张空间地图的新不可变版本；服务端通过版本差异找出受影响的下游空间提案。

### 空间提案与资产

`proposal_canvas` 保存本画布中被设计师选择的关键空间和顺序。每个关键空间有一个 `space_proposal`，并绑定 `space_map` 中的 `space_id`。空间提案卡使用可编辑设计字段，而不是把 Prompt 暴露成主要对象：空间目标、使用场景、空间策略、画面重点、建议视角、材料/家具/灯光语言、继承约束和禁止内容。

效果图是 `space_proposal` 下的变体，不是无归属图片。资产进入 `asset_manifest` 后记录来源、空间归属、角色、输入版本、设计师修改状态和是否被采用。客户提案只读取被明确采用的空间、资产和文案。

### 分支、反馈与上游变化

同一确认方向下的替代探索创建画布分支。分支继承空间地图、方向和约束包的版本引用，但拥有独立空间提案、资产采用状态和布局。第一版支持分支对比与选择，不支持自动或直接合并。

客户只访问由画布派生的提案包。客户反馈锚定具体空间、效果图或说明；设计师确认后才成为设计决策或局部修改。

新的 Brief、项目理解、设计方向、方案约束包或空间地图确认后，现有画布不会被自动改写或重出图。引用旧版本的受影响空间提案和资产标记为 `needs_review`，由设计师保留、局部更新或重新生成。

### 权限与界面边界

第一版桌面端完整编辑。设计师可编辑空间地图、画布、空间提案和资产采用状态；团队成员只读或评论；客户只看提案包和提交反馈。移动端只做查看和评论。

正式界面采用左侧项目依据、中间空间画布、右侧当前节点检查器。它不是通用节点流程图，也不是 CAD 编辑器。

## Consequences

- 画布能承载设计过程，同时保持交付内容与候选内容隔离；
- 空间、效果图和资产具备可追溯归属，后续真实出图可直接读取空间提案；
- 多边形校正、版本差异和画布布局持久化增加了实现复杂度；
- 第一版必须先验证空间地图和人工资产挂载闭环，不能用批量出图掩盖画布语义缺失；
- 真实效果图生成、客户提案导出、实时协作、CAD 编辑和自动分支合并不属于本切片。

## Acceptance boundary

第一版必须支持：从已确认约束包创建空间地图草稿、设计师校正多边形/名称/用途/关系并确认、创建绑定上游版本的提案画布、选择关键空间、创建空间提案卡、手动挂载已有资产、保存独立画布布局、标记上游变化后的受影响内容需要复核，以及画布分支对比与选择。

第一版不支持：墙体或门窗编辑、施工级几何、自动分支合并、真实效果图生成、移动端完整编辑、客户直接编辑画布。
